# 内容提炼框架

## 一、五维提炼表

对着 `transcript.md` 填这五列，每列至少 2 条，填不出来就说明素材不够。

### 1. 核心问题与求知背景

- 用户最初想解决什么？（原话优先，别急着总结成术语）
- 为什么这件事对他重要？（卡点、时间成本、反复踩坑的经历）
- 有没有「表面问题」和「真实问题」的差异？例如表面问「怎么写脚本」，真实需求是「不想每次重复操作」。

写作用途：文章的开篇引入，直接对应读者的同类处境。

### 2. 关键转折

找出对话里方向发生变化的节点，通常是：

- 用户的某次纠正：「不对，我要的不是这个」
- 智能体的主动改道：「换个思路，先看看 X 再决定」
- 被否掉的方案，以及否掉的理由
- 一个原本没想到、后来变成主线的细节

一篇文章有 1-2 个真转折就够了。转折写不出来的稿子，读起来会像流水账。

### 3. 重要结论与方法

- 最终跑通的方案是什么？分几步？
- 关键参数、关键判断依据（为什么选 A 不选 B）
- 有没有可量化的结果（耗时、次数、文件大小、报错消失）

### 4. 坑与解决办法

这是最值钱的部分，读者最爱看。逐条记录：

| 现象 | 原因 | 解法 |
| --- | --- | --- |
| 报错原文或异常表现 | 根因（不是表面原因） | 具体操作，含命令/参数 |

没有坑的对话，通常说明过程被过度简化了——再翻一遍 transcript 找。

### 5. 可复用经验清单

把方法论抽象成 4-6 条可迁移的判断句，标准：

- 去掉具体项目名后，对别的场景依然成立
- 是判断而非步骤（「先确认素材源，再谈自动化」优于「第一步打开文件」）

## 二、真实性校验（交付前逐条过）

- [ ] 每个数字都能在 transcript 里定位到
- [ ] 没有把「我推测」写成「实测表明」
- [ ] 没有为了叙事顺畅补上没发生的因果（「于是他决定…」这类，要有原话支撑）
- [ ] 引用的原话只做删减，不做改写
- [ ] 时间、版本号、文件名与实际一致
- [ ] 失败的过程没有被抹掉（试错是内容价值的一部分）

## 三、脱敏规则

| 类型 | 处理 |
| --- | --- |
| 真实姓名、昵称 | `某同事` / `一位读者` |
| 公司、客户、内部项目名 | `某客户` / `某项目` |
| 本机绝对路径 | `<项目路径>` / `<工作区>` |
| 密钥、token、AppID、AppSecret | `<密钥>`（整段删除，不留前几位） |
| 手机号、邮箱、订单号、IP | 整段删除或用 `<已脱敏>` |
| 未公开的产品名、功能 | 征询用户后再写，或抽象成「某功能」 |
| 内部链接、后台地址 | 删除，或写成「后台页面」 |

判断标准：把文章给一个陌生人看，他能不能反推出你的账号、客户或内部系统。

## 四、素材不足时的处理

- 有效内容 < 300 字：先问用户是否仍要生成。
- 有内容但没有「坑」：把重点放在判断依据和选择逻辑上，不硬编冲突。
- 只有结论没有过程：改写成「结论 + 适用边界」的短文，别假装有完整故事。
